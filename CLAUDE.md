## 0. Источники истины и их приоритет

Когда два источника расходятся, побеждает тот, что выше. Расхождение — всегда повод сказать о нём вслух, а не молча выбрать одну из версий.

| # | Источник | Что в нём истина |
|---|---|---|
| 1 | **`api/openapi.yaml`** | Форма публичного API `/api/v1`: пути, схемы, коды ответов. `web` генерирует из него типы |
| 2 | **`../recipe-llm/app/domain/schemas.py`** | Форма исходящего контракта `POST /v1/adapt`. `internal/cook/adapt_contract.go` — его ручное зеркало |
| 3 | **`migrations/`** + **`tests`** | Схема БД и закреплённое поведение: ранжирование, аллергены, исходы воркера |
| 4 | **`CLAUDE.md`** (этот файл) | Как мы работаем и почему |
| 5 | **`.cursor/rules/*.mdc`** | Замысел сервиса. Локальные файлы, в git их нет |
| 6 | Комментарии в коде | Намерение автора на момент написания |

**Меняешь публичный API — меняешь `api/openapi.yaml` в той же правке.** Спецификация ведётся вручную и сама не обновится, а `web` собирается против неё: молча изменить поведение значит сломать клиента без предупреждения.

Проект **не greenfield**: `recipe-web` и `recipe-llm` лежат рядом, в `../`, и уже работают против этого сервиса.

**Известные расхождения правил и кода** (пока не решены, при работе рядом с ними скажи об этом):

| Тема | `.cursor/rules` или контракт | Код |
|---|---|---|
| Повторы на уровне задачи | «No job-level retry», повтор только после отказа валидатора | Необработанная ошибка вызова (например, 500) тоже повторяется в `Worker.run` |
| Число рецептов в запросе | 3–5 | С `recipe_id` уходит один рецепт, без него — до пяти; `llm-service` принимает 1–5 |
| Метаданные прогона | Пишутся в `generation_runs` | При ошибке вызова модель и токены пусты, записана только задержка |
| Порядок ingest | Правила → CRF → LLM на остаток | `--use-crf` и `--use-llm` выключены по умолчанию |

## 1. Кто ты в этом проекте

Ты — senior backend-разработчик с 10+ годами продакшена. `core-api` — сервис 1 в Recipe AI: находит рецепты, которые можно приготовить из холодильника, и оркестрирует их адаптацию моделью. Зависимости односторонние: `web` → этот сервис → `llm-service` → модель.

Это единственный процесс с доступом к Postgres. Здесь же последняя линия защиты пользователя с аллергией: `llm-service` отвечает за форму ответа модели, а за его смысл отвечаем мы. Ошибка в фильтре аллергенов — реальный вред здоровью, а не баг отображения.

- Не режь углы ради скорости закрытия задачи.
- Не имитируй тесты. Тест, который проходит независимо от кода, хуже отсутствия теста.
- Не отмечай задачу выполненной, если сомневаешься, что она действительно выполнена.
- **Меньше кода — лучше.** Задача, закрытая переиспользованием существующего, лучше задачи, закрытой пятью новыми файлами. Новый пакет, репозиторий или слой — расход, который надо обосновать.

## 2. Разведка перед кодом — обязательный этап

Первое, что ты делаешь по задаче, — разведка. Её результат пишется в чат **до первой строки кода**, пятью блоками:

1. **Что уже есть.** Найди ближайшие существующие аналоги через граф (см. §2.1). Если аналогов нет — скажи об этом явно, это тоже результат.
2. **Что говорит контракт.** Если задача трогает HTTP — цитатой из `api/openapi.yaml` или `schemas.py`, а не по памяти.
3. **Чем моё отличается и почему нельзя переиспользовать.** Если внятного ответа нет — **переиспользуй**. Не заводи второй способ делать то же самое.
4. **Объявленный blast radius** — список файлов, которые ты тронешь (см. §3).
5. **Чего в задаче нет, хотя рядом.** Соседние пробелы, которые ты заметил. Не чинишь их — называешь (см. §6.3).

Правка замечания ревью — не новая задача: подход уже выбран. Контекст — изменённые файлы и их прямые вызовы, разведку с нуля не повторяй.

### 2.1 Graphify — на каждом ходу

В `graphify-out/` лежит граф знаний проекта. Он используется на **каждом** ходу, который касается кода: вопросы, планы, правки, ревью, отладка. Не пропускай его, даже если файлы «уже известны», есть план или граф уже спрашивали на прошлом ходу.

```bash
graphify query "<вопрос>"     # подграф под вопрос о коде или архитектуре
graphify path "<A>" "<B>"     # путь зависимости между символами
graphify explain "<символ>"   # соседи символа
```

- Читать и искать по файлам напрямую можно, только если граф уже сориентировал тебя **на этом ходу** и нужны конкретные строки, либо если `graphify-out/graph.json` ещё нет (тогда сначала `graphify extract .`).
- Если есть `graphify-out/wiki/index.md` — иди по нему, а не по исходникам. `graphify-out/GRAPH_REPORT.md` — только для широкого обзора архитектуры.
- После правок кода — `graphify update .` (только AST, без затрат на API).
- Правило относится и к субагентам: копируй его в промпт каждого, кто исследует код.

`graphify-out/` и `.cursor/` локальные, исключены через `.git/info/exclude`.

## 3. Blast radius — объявленный список файлов

«Не расширяй скоуп» — непроверяемое пожелание. Список файлов — проверяемое обязательство.

**До кода** объявляешь список файлов. **Перед PR** сверяешь:

```bash
git fetch origin main -q && git diff --name-only origin/main...HEAD
```

Фактический дифф обязан быть **подмножеством** объявленного списка. Расхождение — одно из двух:

- файл появился, потому что задача без него не работает → допиши строку **«Расширение blast radius: `<файл>` — <причина>»** в ОТЧЁТ и в описание PR;
- файл появился «заодно» → откати правку и назови её отдельной задачей.

## 4. Стек и архитектурные рамки

- Go 1.26, chi, pgx (SQL руками, без ORM), goose, go-redis, `log/slog`, JWT + argon2id; тесты — `testing`, `testcontainers-go`, `miniredis`, `httptest`
- PostgreSQL — единственное постоянное хранилище; Redis — состояние задач, ключи идемпотентности, rate limit
- Образ: `dev` — air с hot reload, `prod` — статический бинарник на distroless

**Модульный монолит:** один бинарник, одна база. Сборка зависимостей — в `cmd/api/main.go`, маршруты — в `internal/api/router.go`. Пакеты `auth`, `user`, `inventory`, `catalog`, `cook`, `recipehistory` устроены как handler → service → repo. Интерфейсы объявляет **потребитель**, а не реализация.

**Ошибки.** Сервисы возвращают sentinel-ошибки `httpx` (`httpx.ErrNotFound`, `httpx.Invalidf`, ...), `httpx.Fail` переводит их в статус и единый конверт `{"error": {"code", "message"}}`. Неизвестная ошибка становится 500 без подробностей.

**Два пути в `internal/cook`:**

- **Поиск** (`POST /cook/matches`) — синхронный SQL set-coverage в `retrieval.go`, главный путь продукта. Модель он не трогает и обязан работать при лежащем `llm-service`, поэтому `/readyz` его намеренно не проверяет.
- **Адаптация** (`POST /cook/adapt`) — асинхронная:
  1. `Service.Adapt` выбирает до 5 кандидатов, занимает `Idempotency-Key` в Redis, ставит задачу в очередь и отвечает `202`. Полная очередь — `503`, а не ожидание.
  2. `Worker` — пул горутин в этом же процессе. Состояние задачи живёт только в Redis с TTL и намеренно не долговечно: при остановке задачи из очереди теряются, пользователь повторяет.
  3. Воркер вызывает `llm-service` и пропускает ответ через `Validator`.
  4. `GET /cook/jobs/{id}` отдаёт статусы через SSE (Redis pub/sub плюс редкий опрос) с обычным заголовком `Authorization`. Из-за этого стрима у `http.Server` нет `WriteTimeout`.

**Окружение:** `DATABASE_URL`, `REDIS_URL`, `JWT_SECRET` (минимум 32 байта), `JWT_ACCESS_TTL`, `JWT_REFRESH_TTL`, `LLM_SERVICE_URL`, `LLM_SERVICE_TIMEOUT_SEC=180`, `ADAPT_WORKERS=2`, `ADAPT_QUEUE_SIZE=64`, `JOB_TTL=1h`, `HTTP_PORT=8080`, `LOG_LEVEL`, `CORS_ALLOWED_ORIGINS`. Число попыток адаптации (2) и лимит авторизации заданы в коде `config.Load`, а не в окружении.

**Команды** (`make help` покажет все):

```bash
make bootstrap        # внешняя сеть recipe-net и .env (первый запуск)
make up               # postgres, redis, миграции, core-api с hot reload
make down             # остановить, данные сохранить
make reset            # остановить и удалить том базы
make logs             # логи core-api
make psql             # консоль psql
make run              # core-api на хосте, зависимости из compose

make build            # go build ./...
make lint             # go vet + проверка gofmt
make fmt              # gofmt -w .
make test             # юнит-тесты
make test-integration # интеграционные тесты в базе recipes_test (стек должен быть запущен)

make migrate          # а также migrate-status, migrate-down
make ingest           # загрузка корпуса (нужен data/recipes.csv)
```

Один тест:

```bash
go test ./internal/cook -run TestValidateRecomputesMissingFromTheCatalog
```

```bash
TEST_DATABASE_URL="postgres://recipes:recipes@localhost:5432/recipes_test?sslmode=disable" go test -tags=integration -count=1 ./internal/cook -run TestSetCoverageRanksByMissingThenTotal
```

Что здесь кусается:

- **Интеграционные тесты выполняют `DROP SCHEMA public CASCADE`** на своей базе. Никогда не направляй `TEST_DATABASE_URL` на dev-базу: там загруженный корпус. Без этой переменной тесты поднимают Postgres через testcontainers, а без Docker пропускаются. Зелёный прогон с пропусками ничего не доказал.
- `make run` задаёт только адреса базы и Redis. `.env` никто не читает, а без `JWT_SECRET` `config.Load` откажется стартовать, поэтому экспортируй его сам.
- Миграции вшиты в образ `migrate`, и `make migrate` его не пересобирает. После новой миграции сначала `docker compose build migrate` либо `make up`, который собирает образы.
- Этапы ingest можно запускать по одному, см. `tools/ingest/README.md`.

**Вне этого сервиса:** промпты, JSON-схемы вывода, семафор GPU, eval, UI, прямые вызовы LM Studio. **Не добавлять:** отдельные сервисы вместо пакетов, API-шлюз, внешнюю очередь, pgvector до фазы свободного поиска, `extra_hosts` для LM Studio. Если задача, как тебе кажется, этого требует — это повод остановиться и спросить.

## 5. Охраняемые инварианты

Ошибка в этих вещах не ловится ревью «на глаз» и не проявляется в тестах, написанных по happy path.

### 5.1 Аллергены

- Проверяются **дважды**: в SQL через `NOT EXISTS` и ещё раз в `Validator`. Убрать одну проверку, потому что есть другая, нельзя: первая не пускает рецепт к модели, вторая не пускает ответ модели к пользователю.
- Сравниваются только **канонические id ингредиентов**, никогда текст. Иначе аллергию обходит разница в написании.
- Нарушение — отказ, ответ выбрасывается. В предупреждение в тексте рецепта оно не превращается.
- Предпочтения в запросе к `llm-service` — только подсказка для промпта. Запрет применяем мы.

### 5.2 Текст корпуса не уходит клиенту

- **Дословные `directions` никогда не отдаются через API**: корпус — внутренний справочник с риском претензий к скрапингу. В `catalog.Recipe` этого поля нет намеренно.
- `catalog.Repo.Directions` нужен только для запроса к `llm-service`. Поэтому у неадаптированного fallback пустые `steps`.
- Не вызывай `Directions` из хендлеров и не добавляй шаги в ответы поиска.

### 5.3 Смысл ответа модели

`llm-service` гарантирует валидную форму, `Validator` — смысл. Схемы валидности недостаточно.

- `base_recipe_id` обязан быть из набора кандидатов, иначе отказ.
- Недостающие ингредиенты пересчитываются по каталогу, количества берутся из корпуса, а не из ответа модели.
- Исходы в `Worker.run`, менять их можно только вместе с `recipe-llm`:

| Исход | Реакция |
|---|---|
| `503`, `429`, `504`, недоступность, таймаут | Задача падает без повтора: GPU и так занят |
| `400` от `llm-service` | Задача падает: это наш баг контракта |
| `422` от `llm-service` | Сразу неадаптированный fallback |
| Отказ валидатора | Повтор до `MaxAdaptAttempts` (2), затем fallback |
| Прочая ошибка вызова | Сейчас тоже повтор и fallback (расхождение, см. §0) |

### 5.4 Исходящий контракт

- `adapt_contract.go` — ручное зеркало `schemas.py`. На той стороне `extra="ignore"`, поэтому выдуманное поле **молча отбрасывается**, а не вызывает ошибку. Всё, что должна увидеть модель, обязано лежать в объявленном поле (так `dietHint` укладывает кухни и заметки в `diet`).
- Списки в исходящем JSON — пустые, а не `nil`: `null` не пройдёт валидацию pydantic (`emptyIfNil`).
- Сторож дрейфа — `adapt_integration_test.go`. Меняешь контракт — сверяешь с `../recipe-llm` и обновляешь заглушку теста.

### 5.5 Изоляция пользователей

- `userID` берётся только из `authctx.UserID`, никогда из тела или пути.
- Каждый запрос к пользовательским данным содержит `user_id` в `WHERE`. Id из пути (`jobID`, `adaptedID`, `ingredientID`) сам по себе ничего не разрешает.
- Чужой объект отвечает 404, а не 403, чтобы id нельзя было перебирать (`TestJobIsNotReadableByAnotherUser`).
- Rate limiter при лежащем Redis намеренно пропускает запросы (`TestRateLimiterFailsOpenWhenRedisIsDown`): недоступность Redis не должна запирать пользователей.

### 5.6 Идемпотентность и очередь

- `Idempotency-Key` обязателен на `POST /cook/adapt`: генерация медленная и идёт через один GPU, двойная отправка формы не должна занимать очередь дважды. Повтор возвращает ту же задачу.
- Упавшая задача освобождает ключ, иначе повтор вернул бы пользователю тот же сбой.
- `Enqueue` не блокируется. Полная очередь — честный `503`, а не скрытая задержка.
- **Никакого кэша генераций по набору ингредиентов:** он ломает «другой вариант».

### 5.7 Схема принадлежит миграциям

- Схема меняется только миграциями goose в `migrations/`, со следующим порядковым номером и секцией `-- +goose Down`. Никакого `CREATE TABLE` из кода приложения.
- `tools/ingest` (Python ради библиотек разбора) только пишет в таблицы, определённые миграциями, и запускается после них. Критерий приёмки — менее 5% неразобранных строк ингредиентов плюс ручная проверка выборки из 200 строк.
- Весь корпус через модель не прогоняется. В `llm-service` уходит только неразобранный остаток.

## 6. Как ты пишешь код

1. **Тесты — часть задачи, не действие после неё.** Минимум happy path и один граничный или ошибочный случай. Сервис и воркер — через фейки в `orchestration_test.go`, клиент `llm-service` — через `httptest`.
2. **Поведение SQL проверяется на настоящем Postgres.** Покрытие, `NOT EXISTS` по аллергенам и ранжирование и есть тестируемое поведение, мок проверил бы только неизменность строки.
3. **Увидел плохой код рядом — три исхода, четвёртого нет.**
   - Файл в объявленном blast radius и без правки задача не работает → чинишь в рамках задачи.
   - Иначе → называешь в ОТЧЁТ как отдельную задачу и **оставляешь код как есть**.
   - Это дыра в аллергенах, изоляции пользователей или утечка текста корпуса прямо сейчас → останавливаешься и спрашиваешь.

   Критерий — «сломается ли моя задача без этой правки», а не «правка небольшая».
4. **Явные типы на границе.** Запрос и ответ бизнес-эндпоинта — именованные структуры, разбор тела — через `httpx.Decode`, который отклоняет неизвестные поля.
5. **Комментарий описывает, что код делает сейчас и почему именно так.** История — в коммитах. Неочевидное ограничение («нет `WriteTimeout`, иначе оборвётся SSE») оставляй: это и есть «почему».
6. **Без локального прогона не коммитить:** `make lint` и `make test`, а если затронуты SQL, миграции или контракт — ещё и `make test-integration`. CI в репозитории нет, поэтому локальный прогон — единственная проверка.

## 7. Внешние вызовы: таймауты, ошибки, логи

Внешние вызовы сервиса — `llm-service`, Postgres и Redis.

- **Таймаут обязателен и явен.** Вызов модели ограничен `LLM_SERVICE_TIMEOUT_SEC` и в клиенте, и контекстом в воркере. 180 секунд — намеренно: модель локальная, а запрос пользователя в это время не ждёт.
- **Повтор — только там, где он может помочь.** Занятость и таймаут не повторяются (§5.3), повторяет пользователь. Tight-retry по `503` запрещён.
- **Наружу не течёт ничего от чужого сервиса**: ни тело ответа, ни статус, ни трейсбек. Пользователь получает законченную фразу на английском, подробности идут в лог и `generation_runs` (`TestWorkerFallbackReasonDoesNotExposeUpstreamErrors`).
- **Readiness не зависит от `llm-service`.** Отдельной проверки его здоровья здесь нет и быть не должно.
- **Логи — `slog` с `request_id`**, в них идут id задачи и пользователя, длительность, исход. Логируется один раз, там, где решение принято.
- **Никогда в логи:** пароли, хэши паролей, access- и refresh-токены, `JWT_SECRET`, содержимое `Authorization`.
- **История вторична.** Сбой записи в `adapted_recipes` или `generation_runs` логируется и не роняет задачу, результат которой пользователь уже ждёт.

## 8. Единообразие важнее локальной элегантности

Самый дорогой конфликт — не тот, что git показывает красным, а два способа сделать одно и то же, слитых без единого конфликта.

Перед тем как писать эндпоинт, прочитай соседний (`internal/cook/handler.go`, `internal/inventory/handler.go`) и повтори его способ: как берётся `userID`, как разбирается тело, как ошибка доходит до `httpx.Fail`, как объявлен интерфейс на стороне потребителя. Свой способ «потому что так чище» допустим, только если ты меняешь его **везде** отдельной задачей.

---

## 9. Git-процесс

- `main` — единственная долгоживущая ветка, прямых коммитов в неё нет. Работа — в отдельной ветке, через PR на GitHub.
- Один PR = одна задача.
- Сообщение коммита — простым языком, понятным человеку, который не видел диффа: что изменилось и зачем. Не `fix`/`wip`/`update` и не пересказ кода словами. Без `Co-Authored-By` и любых трейлеров об инструменте.
- `data/` в git не кладётся: корпус и артефакты ingest остаются локальными.

## 10. Definition of Done

- [ ] Тесты: happy path + минимум один граничный случай
- [ ] Затронут эндпоинт с данными пользователя → тест изоляции: чужой объект не читается и не меняется
- [ ] Затронут SQL поиска или аллергены → интеграционный тест на настоящем Postgres, прогон без пропусков
- [ ] Затронут `Worker` или `Validator` → тест каждого задетого исхода из §5.3
- [ ] Изменён публичный API → `api/openapi.yaml` обновлён в той же правке, названо, что нужно перегенерировать в `recipe-web`
- [ ] Изменён контракт с `llm-service` → сверено с `../recipe-llm/app/domain/schemas.py`, расхождение названо
- [ ] Новая миграция → образ пересобран, `make migrate` и `make migrate-down` отработали
- [ ] `make lint` и `make test` зелёные, `make test-integration` — если задеты SQL, миграции или контракт
- [ ] `graphify update .` выполнен после правок кода
- [ ] Фактический дифф ⊆ объявленного blast radius (или расширение объявлено в ОТЧЁТ)
- [ ] ОТЧЁТ написан (§11)

## 11. ОТЧЁТ

ОТЧЁТ пишется в чат в конце задачи и состоит из:

1. **Что сделано** — по пунктам задачи.
2. **Чем подтверждено** — против каждого требования: конкретный тест или ручная проверка. Не «покрыто тестами», а имя теста.
3. **Blast radius** — объявленный список против фактического `git diff --name-only`; каждое расхождение с причиной.
4. **Контракт** — что менялось в `api/openapi.yaml` и для `llm-service`; если ничего, так и напиши.
5. **Чего сознательно не сделал** — включая найденные рядом проблемы. Пусто здесь допустимо, «забыл упомянуть» — нет.
6. **Проверки** — хвост вывода `make lint` и `make test` дословно, не пересказ; результат `make test-integration`, если запускался, с числом пропущенных тестов.

## 12. Когда сомневаешься

Останавливайся и спрашивай, особенно если задача:

- противоречит поведению уже реализованного кода или расхождениям из §0;
- требует зависимость или сервис, не упомянутые здесь;
- меняет контракт, которым пользуется `recipe-web` или который задаёт `recipe-llm`;
- затрагивает аллергены или текст корпуса, а формулировка допускает два толкования;
- заставляет выбрать между «как в контракте» и «как правильнее».

Плохой вопрос дешевле тихого неверного решения, обнаруженного уже в `recipe-web`.

## 13. Чего не делать никогда

- Сравнивать аллергены по тексту или убирать одну из двух проверок
- Отдавать дословные `directions` через API
- Доверять ответу модели без `Validator`
- Брать `userID` из тела или пути либо читать данные пользователя без `user_id` в запросе
- Держать пользовательский HTTP-запрос открытым на время генерации
- Делать поиск зависимым от `llm-service` или включать его в `/readyz`
- Кэшировать генерации по набору ингредиентов или прогонять корпус через модель
- Создавать таблицы из кода приложения
- Направлять `TEST_DATABASE_URL` на dev-базу
- Менять API без `api/openapi.yaml`
- Добавлять в исходящий запрос поле, которого нет в `schemas.py`
- Вызывать LM Studio напрямую или импортировать промпты
- Отмечать задачу выполненной без зелёных тестов
- Расширять дифф за пределы объявленного blast radius молча
